# Этап 7: управление подключением репозитория

Ветка `backend/stage-7-repository-lifecycle`. В режиме API команда показывает причину остановки сбора и позволяет восстановить подключение.

## Отключение

`DELETE /api/teams/:teamId/repository` — владелец организации или руководитель проекта, с сессией, Origin и CSRF. В интерфейсе требуется подтвердить остановку сбора.

Операция оставляет Repository, события, авторов и аудит в PostgreSQL. Сбор истории и обработка новых событий останавливаются, активная lease сбрасывается, автоматическая сверка отключается. Повторное отключение безопасно. Установка приложения на GitHub не удаляется.

Наблюдатель и обычный участник не могут остановить сбор всей команды. После отключения сохранённая история остаётся доступной по прежним правилам чтения.

## Повторное подключение

Используется прежний `POST /api/teams/:teamId/repository`: сервер снова проверяет установку приложения, доступ и полномочия администратора GitHub. Восстановить может участник команды или руководитель, имеющий права администратора репозитория на GitHub. Название установки определяется сервером, installation ID вводить не требуется.

Повторно подключается тот же репозиторий по стабильному GitHub ID. Переименование допускается после проверки GitHub, но заменить источник другим репозиторием внутри существующей команды нельзя: сервер возвращает 409, чтобы не смешать историю. После переименования на GitHub можно указать актуальное название в форме восстановления.

Импорт начинается заново с дедупликацией существующих событий. Старые события не удаляются и повторно не начисляются.

## Ошибки

- `USER_DISCONNECTED`: сбор остановлен в TeamPulse; можно подключить повторно.
- `GITHUB_ACCESS_REVOKED`: GitHub прислал удаление/приостановку установки или исключение репозитория из её доступа.
- `GITHUB_ACCESS_DENIED`: запрос истории получил 401/403/404 без признаков rate limit; автоматические повторы прекращаются, нужна проверка доступа и переподключение.
- `GITHUB_RATE_LIMIT`: сохраняется время следующего запроса; импорт продолжится автоматически.
- `HISTORY_REQUEST_FAILED`: временные сбои повторяются с паузой; после пяти ошибок импорт переходит в failed, доступна ручная повторная попытка.

Upstream тела ошибок и credentials не сохраняются и не выдаются пользователю. При проверке подключения выдаются понятные сообщения об установке приложения и необходимости прав администратора.

## Защита от запоздавших заданий

Repository имеет `connectionVersion`. Каждая новая доставка записывает текущую версию; отключение и повторное подключение её меняют. Worker блокирует строку Repository и обрабатывает только события текущей версии. Старые доставки завершаются без записи событий. Это также защищает от гонки между приёмом webhook и отключением.

Для уведомления об отзыве установки сохраняется снимок ID/версий затрагиваемых подключений: старое уведомление не отключает более новое подтверждённое подключение. Старые доставки до миграции без версии относятся к версии 0.

Загрузка истории перед записью проверяет lease и состояние под блокировкой Repository. Ответ сетевого запроса, завершившегося после отключения или переподключения, отбрасывается.

## Проверки

Добавлены тесты ролей/CSRF, сохранения истории, повторного отключения, восстановления, игнорирования старых доставок, запоздалого отзыва установки, потери доступа и ответа истории после сброса lease. Браузерный сценарий проходит отключение с подтверждением и восстановление.

Перед запуском обновить Prisma Client и применить миграции. Стандартные команды: `pnpm lint`, `pnpm build`, `pnpm test`, `pnpm --filter @teampulse/api test:integration`, `pnpm test:e2e:api`. Для последних двух нужна отдельная тестовая БД `_test`.
