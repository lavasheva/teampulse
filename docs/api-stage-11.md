# Этап 11: подключение аналитики

Модуль Вари `@teampulse/analytics` подключён к PostgreSQL, фоновой очереди и интерфейсу API. Формулы и ограничения метаданных описаны в [analytics.md](analytics.md). Демо остаётся отдельным режимом с синтетическими данными.

## Запуск

После `pnpm install --frozen-lockfile` выполнить `pnpm --filter @teampulse/api db:generate`, `pnpm --filter @teampulse/api db:deploy`, `pnpm build`. Затем запустить API и веб-клиент с `VITE_DATA_SOURCE=api`. Для расчётов нужны PostgreSQL, Redis, `GITHUB_EVENTS_ENABLED=true`, `ANALYTICS_ENABLED=true` (по умолчанию). Ключи GitHub остаются на сервере. Аналитика начинает работу после завершения импорта репозитория и обработки ожидающих вебхуков.

## Данные и пересчёт

- `TeamAnalysis` хранит накопленный результат проекта, версию источника/модуля, lease, ошибки и время следующего расчёта. `WeeklySnapshot` хранит результат и сводку каждой недели, включая пустые недели. Ограничение MVP: до 260 недель на проект.
- Новый результат строится из согласованного снимка событий, настроек и текущих участников в транзакции Repeatable Read; JSON проходит валидацию. Вход содержит историю всего проекта для корректного lookback неактивности и `asOf` для незавершённых периодов.
- Изменение события/авторства, настроек, состава или подключения увеличивает `Team.analyticsVersion`. Любое изменение пересчитывает все наблюдаемые недели: старый коммит может повлиять на последующую регулярность. `RecalculationRequest.processedVersion` отмечает только обработанную версию запроса.
- Отдельная очередь BullMQ проверяет команды каждые 3 секунды, выполняет одну задачу одновременно на worker. Lease PostgreSQL защищает команду от двух worker. При сохранении проверяются lease, версия данных, версия подключения и готовность истории. Устаревший результат не публикуется.
- Все недели и итог проекта сохраняются атомарно. GET читает согласованный снимок. Пока идёт импорт/расчёт или при ошибке предыдущий результат остаётся доступен с `stale=true`; незавершённый импорт не выдаётся за пустую активность.
- Ежедневный пересчёт после полуночи UTC обновляет регулярность и пустые недели без новых событий. При сбоях применяется повтор с задержкой до часа. После перезапуска состояние восстанавливается из PostgreSQL; Redis не является единственным хранилищем задания.
- В расчёт входят текущие участники, наблюдатели исключены. Дата вступления предотвращает персональный флаг неактивности до вступления; подтверждённая более ранняя работа сохраняется в баллах. Это пересчёт текущего состава, а не архив исторического состава.

## API и доступ

`GET /api/teams/:teamId/analytics` доступен владельцу/руководителю проекта и членам этой команды. Чужая команда возвращает 404. Ответ `AnalyticsResponse` включает:

- `status`: `not_connected`, `disconnected`, `source_error`, `loading`, `pending`, `error`, `ready`;
- `sourceStatus`, `stale`, `computedAt`, `sourceVersion`, `engineVersion`, `manualAvailableAt`;
- `project`: накопленный результат или `null`;
- `weeks`: недельные результаты и сводки, новые недели первыми.

`POST /api/teams/:teamId/analytics/refresh` требует сессию, Origin и CSRF; доступен руководителю и участнику, но не наблюдателю. При готовом источнике принимает обновление (201), не чаще раза в час на команду (409 при повторе). Расчёт выполняется в фоне. Автоматические обновления не расходуют ручной лимит.

`GET /api/teams/:teamId/activity/:eventId` возвращает событие-основание только внутри доступной команды, без исходного webhook payload и секретов. Подмена команды или eventId не открывает чужие события.

Обзор `/workspace` содержит компактные свежие метрики команд. При ожидании/ошибке не выдаёт нули вместо отсутствующего результата. Полный статус и сохранённый устаревший результат доступны через `/analytics`.

## Интерфейс

В обзоре команды доступны период «Весь проект»/неделя, вклад по категориям, регулярность, Джини, флаги с порогами и раскрываемыми событиями-основаниями, корректировки кода и недельный график баллов. Карточки команд и таблицы участников используют реальные доли. Профиль участника показывает личные показатели; сводки и отчёт используют сохранённые расчёты. Отчёт выводится на печать/PDF средствами браузера. Неполная статистика коммитов и отсутствие измеренного вклада подписаны явно.

## Сводки

По умолчанию `SUMMARY_PROVIDER=template`: ключи и внешние запросы не нужны; в UI стоит «По шаблону». Текущая неделя отмечается как предварительная. Нули не описываются как доказательство равной активности.

Для явного включения ИИ:

- `SUMMARY_PROVIDER=yandexgpt`, `YANDEX_GPT_API_KEY`, `YANDEX_GPT_FOLDER_ID`;
- либо `SUMMARY_PROVIDER=gigachat`, `GIGACHAT_AUTHORIZATION_KEY`.

Внешний запрос выполняется только для последней завершённой наблюдаемой недели; остальные сводки формируются по шаблону. Повторный пересчёт может снова вызвать провайдера. Модуль отправляет агрегаты, а не код/патчи. Ошибка провайдера, неполная конфигурация или неподходящий ответ дают шаблонный fallback и не отменяют метрики. Адаптеры проверены с подставными HTTP-ответами; вызовы настоящих платных провайдеров не проверены.

## Проверка

Модульные тесты покрывают формулы, фильтры, флаги, провайдеров и дату вступления. Интеграционные тесты на отдельной PostgreSQL/Redis проверяют известный результат, пустые недели, права/CSRF/лимит, основания, гонку версий, сохранение результата при ошибке JSON, fallback ИИ и настоящий BullMQ. Браузерный сценарий проходит OAuth → проект → приглашение → подписанный webhook → сопоставление автора → расчёт → метрики/недели/сводки/отчёт. `pnpm test:deploy` проверяет production-сборку, запуск контейнеров, миграции и восстановление копии.

Перед миграцией существующей базы сделать резервную копию по [инструкции этапа 8](api-stage-8.md). Публичный сервер, постоянный webhook URL, домен, почтовые уведомления и реальные ключи ИИ остаются отдельными задачами.
