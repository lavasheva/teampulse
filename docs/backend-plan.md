# Бэкенд TeamPulse: зона ответственности и этапы

Источник: документы «TeamPulse — распределение задач» и «TeamPulse — концепция проекта» из [папки материалов](https://drive.google.com/drive/folders/1N_mME9FLZJ9dprFvm-rLZ35yL3FCB5PZ), просмотрены 18.11.2026.

Саша отвечает за сбор данных: OAuth, организации/проекты/команды, роли и приглашения, GitHub App, вебхуки, Redis/BullMQ, загрузку истории, сопоставление авторов, REST API и запуск еженедельных задач. Почтовые уведомления — желательно после обязательного MVP.

Варя отвечает за расчёт вкладов, защиту от накрутки, флаги и ИИ-сводки. Арина — за интерфейс. Схему Prisma и API-контракт нужно согласовывать с обеими: существующие типы `packages/shared` пока описывают демо, а не готовую серверную модель.

## 1. Основа сервера — завершён

- [x] Приложение NestJS в `apps/api`, строгий TypeScript.
- [x] Конфигурация, локальный CORS, корректное завершение соединений Prisma.
- [x] HTTP liveness и readiness с запросом к PostgreSQL.
- [x] Compose: PostgreSQL, Redis, постоянные тома, healthcheck.
- [x] Начальная модель сбора данных: пользователи, сессии, организации, проекты, руководители, команды, приглашения, репозитории, авторы, события, доставки.
- [x] Начальная SQL-миграция, генерация Prisma Client и валидация схемы.
- [x] Сборка API и HTTP-тесты состояния/конфигурации (14 тестов).
- [x] Миграция применена к PostgreSQL 17, расхождений со схемой нет; HTTP smoke-проверка с настоящей БД проходит на Node.js 24.

На этапе 1 были доступны только health endpoints, Redis поднимался как инфраструктура. Авторизация добавлена на этапе 2, конвейер событий — на этапе 3. Таблицы расчётов (ContributionSnapshot, Flag, Summary) добавляются совместно с аналитикой на этапе 5.

## 2. Вход и доступ

Реализовано в `backend/stage-2-auth-access`: сессии, state/PKCE, CSRF, валидация, основные REST-эндпоинты, доступ по ролям и PostgreSQL-тесты. [Контракт и настройка](api-stage-2.md). Вход с настоящим GitHub проверен 18.11.2026 после регистрации OAuth App; сервер создал активную сессию lavasheva. Фронтенд пока использует демоадаптер. Назначение дополнительных руководителей/наблюдателей через API отложено, их права чтения и ограничения уже проверяются.

1. GitHub OAuth: одноразовый state, callback, получение профиля и подтверждённых email.
2. Серверные сессии: случайный токен, в БД только хеш; HttpOnly cookie, Secure в production, срок жизни, logout. Защита изменяющих запросов от CSRF.
3. Создание организации и проекта с первой командой в транзакции; проверка дат и настроек.
4. Приглашение в проект: случайный токен, хеш, срок, отзыв; вступление в команду после OAuth.
5. Guards/policies: владелец организации, руководитель своего проекта, участник/наблюдатель своей команды. Роль не принимается на доверии от клиента.
6. HTTP-тесты: анонимный запрос, чужая команда, чужой проект, наблюдатель не может менять данные, просроченное приглашение.

Результат: реальный вход → создание проекта → вступление по ссылке; другой пользователь не может читать чужую команду.

## 3. GitHub App и события

Реализовано в `backend/stage-3-github-events`: проверка подключения репозитория через GitHub App, подписанные вебхуки, нормализованный inbox/outbox в PostgreSQL, BullMQ worker, восстановление очереди, повторы и отключение источника. [Контракт и настройка](api-stage-3.md). Настоящая установка App и доставка от GitHub остаются до регистрации App и настройки публичного webhook URL.

1. Установка App с read-only доступом; проверка, что установка и выбранный репозиторий доступны текущему пользователю. Один репозиторий на команду.
2. Проверка HMAC SHA-256 по исходным байтам до разбора тела, ограничение размера запроса.
3. Дедупликация delivery id, сохранение приёма и надёжная постановка в BullMQ. Предусмотреть восстановление между записью в БД и постановкой в Redis (outbox/dispatcher).
4. Worker: push, pull_request, pull_request_review, issues → неизменяемые Event. Идентификатор включает тип события/действие; один PR может дать несколько разных событий. Повторная обработка не создаёт дублей.
5. Повторы с нарастающей паузой до 5 попыток, сохранение ошибок; удаление/отзыв установки отключает репозиторий.
6. Интеграционные тесты подписи, дублей, повторного запуска worker и недоступности Redis.

Результат: событие нашего репозитория доходит до БД без дублей.

## 4. История и авторы

Реализовано в `backend/stage-4-history-identities`: импорт всех веток/PR/review/issues с cursor, прогрессом и lease, статистика файлов без кода, возобновление, ожидание rate limit и суточная сверка. Сопоставление участников по GitHub ID/подтверждённому email, неизвестные авторы, claim с аудитом и запросы пересчёта недель. [Контракт и ограничения](api-stage-4.md). Настоящая история lavasheva/teampulse импортирована и повторно сверена без дублей.

1. Фоновый импорт с пагинацией, checkpoint, прогрессом и возобновлением после сбоя.
2. Общий нормализатор для истории и вебхуков, стабильные внешние ключи.
3. Octokit, короткоживущие installation tokens, ожидание reset при rate limit.
4. Сопоставление по GitHub id и подтверждённым email. Подтверждение неизвестного автора только в своей команде, атомарно и с аудитом; пересчёт затронутых недель.
5. Суточная сверка пропущенных событий.

Результат: подключённый репозиторий заполняется историей; повторный импорт безопасен.

## 5. Контракты и интеграция

В `backend/stage-5-api-integration` добавлены API рабочего пространства, настроек и участника, режим клиента с реальными данными, браузерный сценарий и CI. [Настройка и ограничения](api-stage-5.md). Контракт аналитики пока предложен для согласования; расчёты, сводки и недельный обработчик ожидают модуль Вари. Этап целиком ещё не завершён.

1. Согласовать API DTO и формат Event с фронтендом и аналитикой; демотипы не использовать как модель БД.
2. REST API обзора, команды, участника, неопознанных авторов, настроек, сводок; фильтрация на сервере по доступу.
3. Аналитика получает события и настройки, возвращает метрики/флаги. Схема расчётов и контракт добавляются с Варей.
4. BullMQ-планировщик недельных расчётов и генерации сводок, ручное обновление не чаще раза в час на команду.
5. Сквозной тест от входа до отображения события; CI сборки, типов, тестов и миграций.

Контрольная точка из концепции: к концу четвёртой недели события собственного репозитория должны доходить до экрана. После этого — почтовые уведомления, если остаётся время.
