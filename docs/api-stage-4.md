# Этап 4: история и авторы

Ветка `backend/stage-4-history-identities` от `develop` после PR №16. Новые DTO экспортируются из `@teampulse/shared` (`packages/shared/src/api.ts`). Фронтенд пока работает на демоадаптере.

## Эндпоинты

Все маршруты требуют сессию и доступ к команде. POST дополнительно требует Origin и X-CSRF-Token, как на этапе 2.

| Метод и путь | Результат |
| --- | --- |
| `GET /api/teams/:teamId/repository/sync` | Статус, стадия, обработанные записи, число сохранённых событий, дата последней синхронизации и следующей сверки, время повтора и общий код ошибки. Внутренний cursor/lease не выдаётся |
| `POST /api/teams/:teamId/repository/sync` | Запустить повторную сверку; для failed — продолжить с сохранённой позиции. Разрешено участнику команды и руководителю/владельцу; наблюдателю без роли руководителя запрещено |
| `GET /api/teams/:teamId/events?cursor=<UUID>` | До 100 событий с author и details, `nextCursor` для следующей страницы |
| `GET /api/teams/:teamId/identities/unmatched?cursor=<UUID>` | `{ identities, nextCursor }`: до 100 неизвестных авторов с email/login, количеством событий и `canClaim` |
| `POST /api/teams/:teamId/identities/:identityId/claim` | Подтвердить собственное авторство; тело не требуется, назначить другого пользователя нельзя |

UUID в путях/курсорe проверяется. Чужая команда — 404. Страницы упорядочены по ID; после изменений набора нужно обновить список с первой страницы. Это не экран аналитики и не сортировка по дате активности.

## Загрузка истории

После подключения Repository автоматически имеет pending. При `GITHUB_EVENTS_ENABLED=true` существующий dispatcher добавляет задания истории в BullMQ. Worker чередует короткие порции истории с другими заданиями, не загружает всю историю одним долгим запросом.

Обход:

1. Проверить числовой repository ID и получить актуальное fullName (поддерживает переименование/перенос).
2. С пагинацией получить все ветки, зафиксировать их head SHA.
3. Обойти коммиты от каждого SHA с пагинацией. Общие коммиты веток и уже обогащённые SHA повторно не запрашиваются по одному.
4. Для нового коммита отдельно получить метаданные, статистику и страницы файлов. Сохранить пути, статусы, additions/deletions/changes, прежнее имя при переименовании. Поля patch/code не копируются в БД или курсор.
5. Получить все PR, события открытия/слияния/закрытия и страницы ревью.
6. Получить issues, пропуская PR из этого endpoint; сохранить открытие/закрытие и ID назначенных участников. Если REST не сообщает закрывшего задачу человека, сохраняется неизвестный автор, а не выдуманное назначение.

Тело ревью не сохраняется: только state и признак непустого текста. Удалённые пользователи в review и неизвестные авторы коммитов не мешают сохранению события. GitHub ограничивает список файлов коммита 3000; при достижении границы ставится `filesTruncated`, это ограничение нужно учитывать аналитике.

Исходный `Event.payload` не меняется. Дополнительная статистика хранится в `Event.details`. История и вебхуки используют одни внешние ключи, поэтому импорт/повторная доставка не создают дубликатов.

## Восстановление и сверка

Каждая порция сохраняет следующий cursor в одной транзакции с событиями и статистикой. Lease на Repository предотвращает параллельные изменения cursor; истёкший lease можно подобрать после падения worker. Если репозиторий отключён или установка сменилась во время запроса, ответ не применяется.

429, Retry-After и исчерпанный X-RateLimit-Remaining приводят к ожиданию до разрешённого времени без потери cursor и расходования бюджета обычных сбоев. Для secondary limit без времени reset пауза не менее минуты. Обычный 403 без признаков rate limit не считается лимитом.

После пяти последовательных сбоев одной позиции — failed с общим кодом `HISTORY_REQUEST_FAILED`; ручной POST продолжит с этой позиции. В syncError не сохраняются тела GitHub-ответов, токены или ключи.

После успешного окончания следующая сверка назначается через 24 часа. Сверка повторяет обзор текущих веток, PR/review/issues, пропуская готовую статистику коммитов. Она восстанавливает потерянные вебхуки для объектов, ещё доступных через GitHub API. Коммиты, ставшие недостижимыми после удаления ветки/force-push до приёма вебхука, могут быть недоступны для восстановления.

`syncProcessed` — число обработанных нормализованных записей текущего прохода, включая повторно встреченные PR/issues, а не процент или число новых событий. `_count.events` — фактическое количество событий в БД. Состояние ожидания лимита видно по `syncRetryAt` и `syncError`.

## Сопоставление авторов

Сопоставление ограничено участниками **этой команды** с ролью participant. Руководитель, который не состоит в команде участником, не получает вклад автоматически. Наблюдатели также не получают авторство.

Приоритет:

1. Числовой GitHub ID из GitHub API.
2. Совпадение email с подтверждёнными адресами OAuth-профиля ровно одного участника. Неоднозначное совпадение остаётся неизвестным.
3. Ручное подтверждение неизвестного автора самим участником своей команды.

Username из push не является доказательством личности. GitHub ID другого аккаунта или уже назначенный другому участнику автор блокируют ручное подтверждение (409). Одновременные конфликтующие подтверждения защищены блокировкой строки. Повтор собственного подтверждения идемпотентен.

Подтверждение является заявлением участника, а не криптографической проверкой Git-авторства. Если последующее обогащение от GitHub определит другой числовой ID, сервер исправит привязку и запишет это в аудит. Коммит можно подписать чужим email: статистика сервиса не должна интерпретироваться как доказательство личности автора.

В `IdentityResolution` записываются ручные и автоматические изменения с прежним/новым userId и actorId для ручного действия. Для всех недель, которых касается смена привязки/новые события/статистика, создаётся или обновляется `RecalculationRequest` с версией. Недели начинаются в понедельник UTC. Потребитель этих запросов будет добавлен вместе с аналитикой на этапе 5; на данном этапе готова надёжная постановка пересчёта, а не сам расчёт вкладов.

В конце прохода пересопоставляются уже обогащённые события. Вступление нового участника через приглашение ставит завершённый репозиторий на повторную сверку; активный проход сопоставит его при завершении.

## Проверки

Обычные команды: `pnpm --filter @teampulse/api test`, `build`, `test:smoke`. Интеграционные тесты — `test:integration` с отдельной `TEST_DATABASE_URL` и Redis, как на этапе 3.

Покрыты пагинация веток и файлов, отсутствие кода в cursor/events, единые ключи PR/review/issues, checkpoint/restart, лимиты, пять сбоев и ручной retry, просроченный lease, отключение при запросе, суточная сверка, обработка через настоящий BullMQ, приоритет ID/email, права и гонки claim, аудит и пересчёт нескольких недель.

Ручной импорт настоящего `lavasheva/teampulse` 18.11.2026 завершён: 39 уникальных коммитов, 16 открытий PR и 16 слияний, всего 71 событие. Повторный проход оставил 71 событие и не добавил дублей. Это проверка текущей истории репозитория, не заранее заданное постоянное число.

После вступления lavasheva участником локальной тестовой команды пересопоставление связало с аккаунтом 3 GitIdentity и 13 событий. Проверки на Node.js 24.22.3: lint/build монорепозитория, 38 тестов API, 2 теста клиента, 28 интеграционных тестов PostgreSQL/Redis. Smoke учитывает оба режима readiness: с включённой и выключенной очередью.

Источники: [GitHub commits API](https://docs.github.com/en/rest/commits/commits), [работа с лимитами и повторными запросами](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).
