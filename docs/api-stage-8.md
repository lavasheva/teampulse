# Этап 8: подготовка размещения и резервных копий

Сервер и домен пока не выбраны. Этот этап готовит и локально проверяет контейнерный запуск, но не публикует приложение в интернете и не меняет адреса действующих GitHub Apps.

## Состав

- `deploy/api.Dockerfile`: Node.js 24, NestJS, Linux Prisma Client, миграции. API работает от пользователя `node`, с graceful shutdown и readiness. Prisma CLI оставлен в образе для отдельного задания миграций.
- `deploy/web.Dockerfile`: сборка клиента в режиме API и Caddy. Режим демо не включается серверной переменной после сборки.
- `deploy/compose.yaml`: отдельные PostgreSQL 17, Redis 7, migration job, API и Caddy. Разработка продолжает использовать корневой `compose.yaml` и прежние тома.
- `deploy/backup.cjs`: бинарная резервная копия PostgreSQL и проверка восстановления в изолированном временном контейнере.
- `deploy/check.cjs`: автоматическая репетиция полного запуска, миграций, прокси и восстановления. Работает локально и отдельным заданием CI.

Только Caddy публикует порты. API, PostgreSQL и Redis не имеют опубликованных портов. Caddy передаёт `/api` и `/api/*` в API, остальные клиентские маршруты обслуживает SPA. Отсутствующий API-эндпоинт не превращается в HTML главной страницы. Секреты, `.env`, PEM, локальные архивы и рабочая `.git` исключены из Docker build context.

API доверяет одному прокси только при `TRUST_PROXY_HOPS=1`. Этот режим предназначен для закрытого API за Caddy; прямой публичный порт API открывать нельзя. В разработке по умолчанию proxy trust выключен. Ограничитель запросов хранит состояние в памяти процесса: конфигурация рассчитана на один API, не на несколько реплик.

## Локальная репетиция

Нужны Node.js 24 и запущенный Docker Desktop с Linux containers:

```sh
node deploy/check.cjs
```

Скрипт создаёт уникальный Compose project `teampulse-deploy-check-*`, отдельные тома и случайные loopback-порты. Собирает реальные production-образы, применяет миграции, проверяет frontend/SPA и API через Caddy, приватность портов, PostgreSQL/Redis readiness. Затем создаёт тестовую организацию, снимает dump и восстанавливает его в ещё одном контейнере без сети и без доступа к исходным томам. Проверяет организацию и количество применённых миграций.

В конце удаляются только контейнеры и тома этой временной репетиции. Текущий проект `teampulse` не затрагивается. Тестовый архив, checksum и конфигурация остаются в игнорируемой `deploy/local/` для проверки.

Репетиция использует HTTP только на loopback, без реальных OAuth/App credentials. Она проверяет контейнеры и маршрутизацию, но не выдачу публичного TLS-сертификата, DNS или вход через настоящий GitHub. Эти проверки выполняются при настройке выбранного сервера.

## Будущий первый запуск на сервере Linux

1. Установить Docker Engine и Compose. Подготовить доменное имя с DNS, указывающим на сервер, и доступные снаружи порты 80/443.
2. Получить проверенную версию репозитория и зафиксировать commit для возможности отката.
3. Скопировать `deploy/.env.example` в `deploy/.env`. Задать случайный пароль PostgreSQL и тот же пароль в `DATABASE_URL`; hex-строка позволяет избежать специальных символов URL. Установить реальные `SITE_ADDRESS`, `WEB_ORIGIN=https://домен`, OAuth callback `https://домен/api/auth/github/callback`.
4. Заполнить OAuth/App ID, slug, client secret и webhook secret. Private key хранить вне репозитория; `GITHUB_APP_PRIVATE_KEY_FILE` — абсолютный путь на сервере. Он монтируется как read-only Compose secret. Файл должен читаться UID 1000, от которого работает API (например, владелец UID 1000 и права 0600). Сам `deploy/.env` также ограничить правами 0600.
5. Выполнить из корня:

```sh
docker compose --project-name teampulse-prod --env-file deploy/.env --file deploy/compose.yaml up --build -d --wait
```

Миграции выполняются до запуска API. Caddy получает/обновляет HTTPS-сертификат для заданного домена; его состояние сохраняется в отдельных томах. Не использовать `.example` как настоящий адрес.

6. Проверить `https://домен/api/health/ready`, HTTPS и клиентские маршруты. Обновить URL OAuth App и GitHub App webhook на `https://домен/api/webhooks/github`; выполнить реальный вход и тестовую доставку GitHub. Установку GitHub App на репозиторий проверять отдельно.

Команды, печатающие полный Compose config или env, могут раскрыть credentials; для просмотра состояния использовать `ps`, а не публиковать содержимое `.env`.

## Резервная копия

Команды работают из корня на Windows и Linux; не используют перенаправление бинарного stdout через PowerShell:

```sh
# Рабочая локальная база разработки:
node deploy/backup.cjs backup --project=teampulse --compose=compose.yaml --out=backups

# Будущий сервер:
node deploy/backup.cjs backup --project=teampulse-prod --compose=deploy/compose.yaml --env=deploy/.env --out=backups

# Подставить путь, напечатанный командой backup:
node deploy/backup.cjs verify --archive=backups/ИМЯ.dump
```

Архив custom-format создаётся через `pg_dump`, сначала в `.partial`, затем атомарно переименовывается. Рядом сохраняется SHA-256. Проверка сначала сверяет checksum, затем выполняет настоящий `pg_restore --exit-on-error --single-transaction` в новой базе и читает таблицы приложения. Исходная база не изменяется. Это проверка пригодности архива к восстановлению, а не автоматический откат production.

Архив содержит пользовательские данные и хеши сессий. Ограничить доступ к каталогу; на Linux скрипт создаёт каталог 0700 и файлы 0600, на Windows права определяются ACL каталога. Хранить копии также вне сервера, желательно в зашифрованном хранилище. Локальный dump на том же диске не защищает от потери сервера.

После выбора сервера настроить ежедневное резервное копирование, срок хранения и периодическую проверку восстановления. Этот этап не создаёт системное расписание и не удаляет старые архивы автоматически. Перед каждым обновлением делать отдельную копию. Отдельно сохранять `.env` и PEM в защищённом хранилище: `pg_dump` их не содержит.

## Обновление и восстановление

Перед обновлением: снять и проверить архив, записать текущий commit/tag образов, затем собрать/запустить новую версию той же командой Compose. Переменную `TEAMPULSE_IMAGE_TAG` использовать для различимых версий. API и migration job должны использовать один образ.

`docker compose down` без `--volumes` сохраняет данные. Не применять `down --volumes` к рабочему `teampulse-prod`: это удалит данные PostgreSQL, Redis и состояние сертификатов.

Для аварийного восстановления остановить запись API, сначала восстановить архив в новую пустую БД, проверить миграции и количество объектов, затем переключить `DATABASE_URL` и перезапустить API. Старая база остаётся до проверки новой. Восстановление рабочей базы намеренно не автоматизировано разрушающей командой. Откат только к старому образу после новой миграции может быть несовместим со схемой — проверять до обновления.

## Основания конфигурации

Маршрутизация SPA/API соответствует [паттернам Caddy](https://caddyserver.com/docs/caddyfile/patterns), ключ монтируется по [механизму Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/). Формат архивов и восстановление опираются на [pg_dump 17](https://www.postgresql.org/docs/17/app-pgdump.html) и [pg_restore 17](https://www.postgresql.org/docs/17/app-pgrestore.html). Доверие reverse proxy включается явно для [Nest rate limiting](https://docs.nestjs.com/security/rate-limiting#proxies).
