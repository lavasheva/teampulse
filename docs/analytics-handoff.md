# Аналитика TeamPulse: состояние и план доводки

Модуль расчёта в [PR №24](https://github.com/lavasheva/teampulse/pull/24) готов по ТЗ Вари от 18 ноября. Аналитика как функция продукта ещё не закончена. Нужно связать расчёт с реальными событиями и экранами, а затем пройти сквозную проверку. В концепции есть более подробные требования к данным и сводкам. Они отмечены ниже, чтобы команда могла закрыть их или явно согласовать упрощение для защиты.

За правила отвечает Варя, за сбор данных, пересчёт и API — Саша, за отображение — Арина. В исходной концепции описан результат для преподавателя, а документ «Задачи Вари по аналитике» допускает расчёт по доступным метаданным и оставляет хранение, очередь и расписание бэкенду.

| Флаги | Все шесть готовы. Тишина участника и команды, перекос, поздний всплеск, высокая доля исключённых строк и события без сопоставленного автора. У каждого сигнала есть область действия, период, значение, порог и объяснение. |

Экспорт движка находится в [packages/analytics/src/index.ts](../packages/analytics/src/index.ts), общий контракт — в [packages/shared/src/analytics.ts](../packages/shared/src/analytics.ts), входной снимок — в [apps/api/src/analytics/input.service.ts](../apps/api/src/analytics/input.service.ts).

## Саша: подключить один расчёт от GitHub до API

1. **Начать с одной команды и завершённой недели.** Подключить `@teampulse/analytics` к API или воркеру и собирать пакет перед потребителем. Проверить запуск собранного CommonJS-пакета в CI и контейнере. Продолжать использовать права доступа проекта и команды для всех новых ответов с аналитикой.
2. **Собрать пригодный снимок.** Использовать `AnalyticsInputService.week` как основу. В переходе от Prisma к `WeeklyAnalyticsInput` проверить JSON весов, порогов, событий и деталей. Неделя идёт с понедельника по UTC, конец интервала исключается, последний день проекта включается. Для текущей недели передать `asOf`. Подтвердить покрытие истории до показа тишины. Команда без репозитория и незавершённая синхронизация должны получать статус источника. Завершённая и покрытая неделя без событий должна рассчитываться как пустая.
3. **Обрабатывать повторные пересчёты.** Воркера привязать к существующим `RecalculationRequest` с ключом «команда и начало недели». Записать расчёт вместе с `sourceVersion` и `engineVersion`. Перед записью проверить, что запрос всё ещё актуален, чтобы медленная задача не перезаписала новое состояние. Один и тот же снимок при повторе заменяет результат. Новое событие, изменение настроек, новое сопоставление автора и уточнение статистики должны обновлять затронутый расчёт.
4. **Проверить связанные периоды.** Пустые завершённые недели тоже нужно ставить в очередь. Сейчас обновление настроек создаёт запросы по датам существующих событий. При изменении дат, весов, состава или порогов пересчитать также затронутые сохранённые и пустые недели. Если семидневная пауза пересекает границу недели, передать фактически покрытую историю через `historyStartsOn`. При изменении старого события могут потребовать пересчёта более поздние недели, которые использовали его как историю. `calculateProject` должен получать события за весь проект, текущие веса и согласованный состав.
5. **Вернуть расчёт через API.** Отдать недельный и итоговый расчёты, историю недельных результатов и ссылки на подтверждающие события с проверкой доступа. Предусмотреть статусы для отсутствия подключения, синхронизации, готового отчёта и сбоя. У готового ответа показать период, момент актуальности и признак неполных данных. Если пересчёт идёт, можно показывать последний готовый результат с датой его актуальности.
6. **Включить недельные сводки после вывода метрик.** Генерировать после расчёта за завершённую неделю. Сохранять `text`, `source`, использованные версии и дату обновления. Защитить кнопку обновления от вызова чаще раза в час на команду. На сбой провайдера применять ограниченные фоновые повторы и возвращать шаблон. Расчёт и API метрик должны оставаться доступны. Сводка проекта показывает по одному абзацу на команду. Электронная рассылка в концепции отмечена как желательная.

## Арина: заполнить существующие экраны результатами

| Экран | Что показать |
| --- | --- |
| Обзор проекта | Все команды, последнюю учитываемую активность, наиболее серьёзные флаги и Джини. Сортировать команды с рисками выше. Для недельного обзора использовать сохранённые командные сводки. |
| Страница команды | Вклад по видам работ, график по сохранённым неделям, флаги, ленту GitHub и события без участника. В настройках дать руководителю доступ к весам, порогам и вехам проекта. |
| Карточка участника | `totalPoints`, исходные баллы `work`, `sharePercent`, `categoryShares`, активные дни и средний перерыв. Показать PR и задачи со ссылками на события, причины и объём исключений. |
| Сводки | Историю по неделям, дату, текст и отметку «По шаблону» при `source = template`. При временном сбое оставить последний готовый текст и показать статус обновления. |
| Итоговый отчёт | Общий вклад за проект, заметные работы, историю флагов и печатную версию. Для долей брать результат `calculateProject`. |

У флага нужны причина, конкретный участник или команда, фактическое значение, порог и период. Примеры читаемых подписей — «Тишина участника», «Перекос вклада», «Высокая доля исключённых строк». По возможности добавить переход к событиям из `evidenceEventIds`. При `adjustments[].lines = null` количество строк неизвестно. Для пустой или нулевой недели показать причину и контекст. Нулевые доли и Джини при нулевой сумме сами по себе не свидетельствуют о равном вкладе. Пояснить, что учитывается наблюдаемая работа в GitHub.

Локальная страница `/analytics-local.html`, если запущен демонстрационный сервер, показывает настоящий расчёт на учебных событиях. Сквозная проверка должна идти через обычные экраны TeamPulse в режиме API.

## Где концепция требует дополнительных данных

| Расхождение | Что нужно сделать или согласовать |
| --- | --- |
| Пробельные правки, точная классификация бинарных и сгенерированных файлов | Саша добавляет нормализованные признаки или число строк после сравнения без пробелов. Для бинарных и генерируемых файлов нужны явные признаки, когда их можно получить. Варя подключает данные к существующим корректировкам и добавляет тесты. Пока подсказка должна обозначать эвристику по пути и неполноту статистики. |
| Обогащение событий после вебхука | Сборщик уже пишет статистику коммитов и признаки ревью при импорте истории. У новых событий часть этих деталей изначально отсутствует. Догружать минимум нужных метаданных и инициировать пересчёт. Чтобы считать комментарии к строкам, нужен отдельный признак или счётчик. Пока действует начисление по доступному статусу и наличию текста ревью. |
| Squash и назначенные задачи | Для предотвращения повторного учёта кода после squash нужны SHA результирующего и исходных коммитов. Для вклада по назначенной задаче нужен исполнитель на момент закрытия и согласованное правило атрибуции. Текущий снимок назначения и автор закрытия отвечают на разные вопросы. |
| Тишина после вступления в команду | В БД есть `TeamMembership.joinedAt`, но в текущем снимке только текущий состав. Согласовать политику для новых участников и истории состава. Для реализации передавать даты участия. Проверка должна отличать семь дней в команде без действий от вступления вчера. |
| Сводка в духе «сделала авторизацию» | Сейчас доступны агрегаты и сигналы. Для содержательных выводов нужен проверяемый список заметных PR или задач с типом, кратким безопасным названием и ссылкой на событие. Использовать эти факты локально в тексте и передавать модели только согласованный минимум. Привязать выбранные тезисы к источникам и сохранить шаблон при недостатке данных. |
| ИИ в реальном окружении | После получения ключей проверить один настроенный адаптер на тестовом проекте с разрешения владельца ключа. Проверить штатный результат и возврат к шаблону при недоступности. Код и секреты остаются за пределами данных сводки. |
| Три–четыре эталонных репозитория | Сейчас есть модульные наборы событий и раздельные интеграционные тесты бэкенда. Подготовить контролируемые репозитории или записанные наборы событий с ожидаемыми результатами и прогнать их через сбор, воркер и API. Хотя бы один подключённый GitHub-репозиторий нужен для демонстрации полного пути. |

Порядок доводки — сначала один живой отчёт от GitHub до экрана, затем пересчёт и недельная история, после них сводки и точность дополнительных сигналов. Кнопка «Что сделал участник?» и отметки вех на графиках в концепции относятся к желательным возможностям.

## Приёмка перед защитой

- [ ] Пройти сценарий с тестовым репозиторием и обычным клиентом в режиме API. Подключить репозиторий, дождаться синхронизации, взять завершённую неделю и сверить баллы, доли и флаги с ручным расчётом.
- [ ] Использовать четыре эталонных сценария. Равные участники дают Джини 0. В команде из трёх один человек выше 60%, а другой без активности семь дней, дают два разных флага. Коммит с 40 допустимыми и 90 исключёнными строками даёт 2 исходных балла кода и флаг 69,23%. Покрытая неделя без событий показывает тишину команды и шаблонную сводку.
- [ ] Один и тот же вебхук отправить дважды. Затем подтвердить автора коммита, изменить вес категории и сравнить результат до и после. Доля меняется там, где изменились исходные данные. Совпадающие расчёты не суммируются. Старая задача не затирает более новую.
- [ ] Сравнить источник, который ещё синхронизируется, и реально пустую неделю. Проверить границу UTC, историю для порога больше семи дней и последнюю неделю проекта.
- [ ] Проверить перекос при 60% и чуть выше, исключения при 50% и чуть выше, поздний всплеск вокруг вехи. Из карточки флага можно понять, какие значения и события его вызвали.
- [ ] При сбое ИИ открыть отчёт и шаблонную сводку. При входе участника чужая команда остаётся недоступна. Итоговая печатная страница содержит расчёт за проект и историю флагов.

Для проверки именно пакета используются `pnpm --filter @teampulse/analytics build` и `pnpm --filter @teampulse/analytics test`. После интеграции расширить существующие [тесты API](../apps/api/test/client-api.integration.ts) и [браузерные тесты](../apps/web/e2e) сценарием с готовой аналитикой.
